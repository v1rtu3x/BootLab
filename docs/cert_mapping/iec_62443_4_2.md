# IEC 62443-4-2 — evidence worksheet

[Project overview](../../README.md) · [Visual walkthrough](../../WALKTHROUGH.md) · [Documentation map](../README.md#assurance-mappings)

[IEC 62443-4-2:2019](https://webstore.iec.ch/en/publication/34421) defines technical security requirements for industrial automation and control system components. Select exact component requirements and any applicable enhancements from the edition used in the assessment. The topics below are project engineering labels, not official component-requirement or security-level identifiers.

## 01 / Keep the component boundary explicit

```text
component requirement -> configured component -> selected check -> retained result
        target                assumptions          experiment        review
```

A host-side verifier test, an MCUboot simulator test, and a deployed device test have different boundaries. Record which one supports the claimed component capability.

## 02 / Candidate engineering topics

| Component topic | Useful BootLab material | Boundary to retain |
|---|---|---|
| Executable-image integrity | S01, S03, A05, A06 | Offline corrupted-byte checks |
| Image authentication | S02, S06, A07, A08 | Runtime bad-signature test is distinct from host key verification |
| Update format and size handling | S04, S05 | Host parser and simulated slot-size tests are different paths |
| Boot/update behavior | P01–P04, overwrite variants | Some IDs share tests or encounter configuration-specific early returns |
| Version acceptance policy | V01/V02 | Actual Cargo features select overwrite; disabled helper skips the check |
| Recovery behavior | F02/F03/F04/F02O | Numeric modeled interruptions, with no measured physical fault resistance |
| Trust-anchor maintenance | K01–K03 | Single-key host selection; no device trust-store update |

Passing these cases does not assign a component security level. Product configuration, threat assumptions, other component requirements, and integration evidence remain part of the assessment.

## 03 / Build a reviewable evidence row

Use a product-owned requirement ID and the exact clause reference selected for the assessment. The subject headings above are engineering topics, not official requirement identifiers.

| Field | Fill in for the product |
|---|---|
| Product requirement | `<requirement ID and testable statement>` |
| Source reference | `<edition/version and exact applicable clause>` |
| Threat / rationale | `<threat ID and reason this check is relevant>` |
| Effective configuration | `<MCUboot revision, local patch, Cargo features or board setup>` |
| Executed case | `<scenario ID, backend, actual test/input>` |
| Retained evidence | `<run archive>/evidence/runs/<run-id>/<id>/record.json`, stdout, stderr, input hashes |
| Observation and limit | `<what happened; what the experiment did not observe>` |
| Review | `<owner, date, conclusion, unresolved work>` |

From `BootLab/`, after preparing the environment and corpus:

```bash
bootlab run-matrix
bootlab sanitize-report
```

Use the resulting records and logs, not the scenario name alone. Read [the test matrix](../TEST_MATRIX.md) and [evidence limitations](../LIMITATIONS.md) before filling in the conclusion. A sanitized summary is a sharing aid; retain the raw experiment in the internal run archive.

## 04 / Interpretation

This worksheet organizes engineering evidence. Passing BootLab scenarios does not establish product compliance, certification, or a complete assessment. The product's scope, applicable requirements, implementation, and other lifecycle evidence need their own review.
