# Contributing to BootLab

[Project overview](README.md) · [Visual walkthrough](WALKTHROUGH.md) · [Documentation map](docs/README.md)

**Make the executed check, its evidence, and its explanation agree.** A useful contribution makes a security question easier to reproduce and gives the reviewer a clear way to judge the result.

## 01 / Prepare the development environment

Run from `BootLab/` with the vendored MCUboot sources and their dependencies present:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
python -m pip install ./vendor/mcuboot/scripts
pytest -v
```

Use [reproducibility](docs/REPRODUCIBILITY.md) for the complete runtime workflow. The harness tests and the MCUboot scenario matrix exercise different layers; a passing pytest run is not a simulator result.

## 03 / Add a scenario with a precise claim

Start by describing **the input, the executed behavior, and the observable outcome**. Select a backend that can observe that outcome. The current simulator adapter selects upstream tests; it does not automatically inject the YAML's named images or configure itself from a profile file.

This shortened example shows the structure of the existing S01 case. Use a unique ID and filename for a new case; do not add this example as a duplicate.

```yaml
id: S01
name: payload-modification-rejected
category: integrity
profile: mcuboot_swap_reference
operation: boot
backend: imgtool_verify
backend_args:
  image: v2.0.0-trusted-payload-flip.bin
  key_id: dev-trusted
  key_type: ecdsa-p256
fault:
  type: none
expect:
  verify_rejected: true
  outcome_in:
    - secure_refusal
notes: |
  Host verifier case. Inspect stderr to distinguish clean refusal
  from an unexpected parser failure.
```

1. Create a YAML file under `scenarios/` using the [schema](src/bootlab/scenario.py). Use a descriptive name and a unique ID such as `S07`.
2. Set effective `backend_args`. A simulator case needs a meaningful `cargo_test` and `cargo_features`; a verifier case needs an existing corpus image and the intended key.
3. Add the image recipe in `images.py` if the corpus does not contain the required input. Confirm that the manifest identifies the actual generated bytes.
4. Read the selected upstream test. Check for early returns, feature gates, and a substring filter matching multiple tests.
5. Define the oracle around observations. A YAML expectation that is never consumed cannot establish the claimed behavior.
6. Add the row to [the matrix](docs/TEST_MATRIX.md) and a question, diagram, backend explanation, and command to [the walkthrough](WALKTHROUGH.md).
7. Run the targeted case. If runtime behavior or shared fixtures changed, run the affected family and the full matrix before presenting a result.

```bash
bootlab build-corpus
bootlab run-scenario scenarios/S01_payload_flip.yaml
# Read evidence/S01/record.json, stdout.txt, and stderr.txt.
```

A negative verifier case currently accepts any nonzero verifier exit. An unexpected traceback is a separate finding, even when the wrapper records a pass. Follow [the findings policy](docs/FINDINGS_POLICY.md).

## 04 / Change the harness or add a command

Add commands through Click in [cli.py](src/bootlab/cli.py). Document their working directory, prerequisites, output paths, exit behavior, and whether existing evidence is replaced. Keep generated keys, image bytes, and reports covered by `.gitignore`.

Use tests that challenge the behavior: a wrong signer, no matched test, unexpected process failure, or incorrect state should not silently satisfy a stronger claim. Keep assertions independent of the same configuration value used to produce the result. Update tests when changing the oracle contract, then run `pytest -v` and the relevant runtime cases.

For a prose-only or visual-only edit, check links, commands, captions, and rendered assets. Re-running a hardware or simulator campaign is unnecessary unless its behavior changed or a new result is being claimed.

## 05 / Maintain visual assets

The committed GIFs and PNGs are generated by `source/render_bootlab.py`. From the project root, install Pillow in the active environment and run:

```bash
python -m pip install Pillow
./scripts/generate-animations.sh
```

The renderer requires DejaVu Sans Mono, or explicit `--font` and `--bold-font` paths. Review both themes in [the gallery](preview.html), including still frames and the mobile header. Keep captions, alt text, and reduced-motion PNGs aligned with the depicted behavior.

When the number or grouping of scenarios changes, update the README, walkthrough, matrix, and the header's coverage labels in the renderer together. Graphics must not display fabricated live verdicts.

## 06 / Changes to the simulator

The current fault extension lives in [fault_campaign.rs](vendor/mcuboot/sim/tests/fault_campaign.rs) and helpers in [image.rs](vendor/mcuboot/sim/src/image.rs). Keep any changes narrow and record the base MCUboot revision plus local patch state. [Fault-injection reference](docs/FAULT_INJECTION.md) explain the current interface.

Do not include production signing material in contributions. Retain the case record and raw logs needed for review, and inspect a sanitized report before sharing it. An upstream submission needs its own concrete issue or PR reference; a local patch alone does not establish acceptance.
